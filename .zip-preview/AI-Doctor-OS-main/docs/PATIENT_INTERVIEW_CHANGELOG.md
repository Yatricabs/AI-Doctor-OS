### Chat input and layout

- Corrected invisible typed text styling.

### Attachments

- Local suggestions appear immediately while API results update in the background.
- Keyboard Up/Down and Enter selection are supported.

## 4. Semantic Edit and Replay

Editing is semantic rather than visual:

1. The edited answer becomes authoritative.
2. Messages and answers derived from the old value are invalidated.
3. Questions, QA log, report, result, urgency, clarification, and reasoning state are cleared where dependent.
4. The flow resumes from the edited step.
5. Context and reasoning run against the corrected value.

Cancel is non-mutating:

- The original answer remains unchanged.
- Temporary editor text is discarded.
- The previous interview step is restored.
- No AI request or downstream question is generated by Cancel.

## 5. Phase 1 — Context, Contradictions, and Safety

**Status:** Implemented and browser-verified.

Every accepted non-phone answer is evaluated through this boundary:

```text
latest answer
→ accumulated structured answers
→ previous patient messages
→ follow-up QA
→ clarification history
→ uploaded-file metadata
→ deterministic red-flag check
→ semantic consistency reasoning
→ validated application outcome
```

Allowed reasoning outcomes:

- `CONTINUE`
- `NEEDS_CLARIFICATION`
- `SAFETY_CONCERN`

The model cannot return arbitrary application steps or mutate state. The application validates the result and controls all transitions.

Verified browser scenarios:

- `SEX = Man` + periods statement → clarification before duration.
- `SEX = Woman` + periods statement → no false contradiction.
- `SEX = Transgender Man` + menstrual statement → context-aware clarification without simplistic binary assumptions.
- `SEX = Man` + urine bleeding → not interpreted as menstrual bleeding.
- Editing `SEX` from Man to Woman removes old downstream complaint/clarification state and rebuilds the flow.

## 6. Phase 2 — Adaptive Next-Best Question

**Status:** Implemented and browser-verified on 2026-09-16.

Phase 1 decides whether an answer is consistent, ambiguous, contradictory, or safety-relevant. Phase 2 will improve only the `CONTINUE` branch.

Transitions that remain deterministic:

- Patient classification and phone lookup
- Name, age, `SEX`, and location collection
- Appointment date and time
- Database match choices
- Safety guards
- Edit invalidation/replay integrity
- Final persistence and error recovery

Clinical transitions suitable for adaptive selection:

- Chief complaint → highest-value missing clinical question
- Duration → severity, associated symptoms, history, medication, treatment, or report question
- Previous treatment/report answer → next missing clinical dimension
- Every adaptive answer → newly evaluated next-best question
- Sufficient coverage → final report generation

Proposed allowlisted decision contract:

```ts
type NextClinicalAction =
  | "CONTINUE_WITH_QUESTION"
  | "ASK_CLARIFICATION"
  | "ASK_SAFETY_QUESTION"
  | "REQUEST_DURATION"
  | "REQUEST_SEVERITY"
  | "REQUEST_ASSOCIATED_SYMPTOMS"
  | "REQUEST_RELEVANT_HISTORY"
  | "REQUEST_TREATMENT_HISTORY"
  | "REQUEST_MEDICATION_HISTORY"
  | "REQUEST_REPORT"
  | "READY_TO_FINALIZE";

type NextBestDecision = {
  action: NextClinicalAction;
  question: string;
  coverageTarget: string | null;
  rationale: string;
  missingInformation: string[];
  safetyConcern: boolean;
  readyToFinalize: boolean;
};
```

Integration order:

```text
deterministic safety check
→ Phase 1 contradiction/clarification reasoning
→ if CONTINUE: Phase 2 next-best-question decision
→ schema and allowlist validation
→ application-controlled transition
```

Implementation details:

- `lib/next-best-question.ts` defines the allowlisted action and coverage schemas.
- The model returns one decision after each clinical answer; question batches are no longer generated or walked sequentially.
- Existing `qaLog` stores the answer plus an optional allowlisted `coverageTarget`.
- Structured duration, treatment-history, and report answers continue using their existing fields and UI steps.
- The application rejects malformed actions, arbitrary coverage keys, repeated covered targets, overlong or empty questions, and premature finalization.
- `READY_TO_FINALIZE` requires application-validated minimum coverage: duration, red-flag coverage, and at least three adaptive answers.
- Invalid or unavailable AI responses use a bounded allowlisted fallback targeting uncovered information.
- Phase 1 contradiction and deterministic red-flag checks always run before Phase 2.
- Duplicate transition paths were consolidated into `continueAfterAnswer()`; the generated-question array and index progression were removed.

Hard-coded clinical transitions removed:

- Chief complaint always asking duration
- Duration always asking previous consultation
- Previous consultation always asking reports
- Reports always generating a batch of questions
- Adaptive answers walking through a pre-generated array

Browser verification:

- Generic headache complaint selected severity before duration.
- Chest-pressure complaint selected a safety-focused question before duration.
- A complaint already containing duration did not repeat duration.
- A complaint already expressing high severity did not repeat severity and asked associated symptoms.
- Phase 1 contradiction and deterministic red-flag handling retained priority.
- Editing a complaint cleared old coverage/questions and recalculated the next-best question.
- A complete adaptive interview reached the final report with the authoritative complaint.
- Real phone lookup still returned Rohan Mehta for `9820011021`.

No web search, internet research, or external medical retrieval is included in Phase 2.

## Phase 3A - Semantic Context Assessment

**Status:** Implemented and browser-verified on 2026-09-16.

Phase 1 previously received raw text and structured context, but it had no validated representation of clinically meaningful anatomy/body-site, symptom, medication, diagnosis, treatment, or history facts in the latest answer. A model `CONTINUE` result could therefore reach the next-best-question fallback without a semantic conflict being explicitly represented.

The new boundary is general rather than a list of `SEX + symptom` rules:

```text
patient answer
-> allowed semantic fact extraction
-> accumulated semantic evidence
-> context-consistency assessment
-> Phase 1 contradiction/safety assessment
-> Phase 2 next-best-question decision
-> bounded fallback only when no semantic conflict is known
```

`lib/semantic-context.ts` validates only derived evidence: anatomical/body-structure references, body location/site, symptom and symptom characteristics, medication/diagnosis/treatment/history claims, and explicit reproductive claims. Each fact has an allowlisted kind, polarity, confidence, and source text. Facts are evidence only: they cannot overwrite authoritative structured fields such as `answers.sex`.

The semantic assessment returns `CONSISTENT`, `AMBIGUOUS`, or `NEEDS_CLARIFICATION`. A non-consistent result stops the flow before Phase 1 `CONTINUE`, Phase 2 selection, or deterministic fallback. The application renders the validated clarification and waits for a patient answer; it neither diagnoses nor silently changes `SEX`.

Semantic facts are cleared and rebuilt whenever Edit/Replay invalidates downstream state. Editing `SEX` from Man to Woman removes the old downstream semantic conflict, replays deterministic intake, and assesses a new complaint against the corrected authoritative context.

Browser verification through the real component/event/state path:

- Man + `mere vagina me white discharge ho raha hai` -> clarification; no duration question before clarification.
- Woman + the same complaint -> no false conflict; normal adaptive severity question.
- Man + `mere penis se white discharge ho raha hai` -> no false vaginal classification; normal adaptive severity question.
- Man + vaginal complaint, then Edit `SEX` to Woman -> stale conflict removed and next clinical decision recalculated.
- Phase 1 menstrual contradiction, deterministic red flags, clinical replay, classification edits, and real phone lookup also passed.

The deterministic browser adapter supplies only external model-boundary responses. It does not inject Redux state, mutate answers, bypass replay, fake rendered UI, or mock the phone database lookup.
